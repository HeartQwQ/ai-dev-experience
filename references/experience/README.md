## 四种内容层级

1. **通用方法**：保护无关改动、说明范围、核对契约、保持证据和结论一致。
2. **技术栈专项**：依赖语言、框架、数据库、运行时或浏览器能力；使用前核对项目版本。
3. **项目约定或可选预设**：目录、端口、单实例、版本制度、视觉参数等；项目选定后才约束该项目。
4. **历史案例**：帮助识别失败模式；缺少环境和复现记录的数字不能当作现测结果或容量保证。

各篇的默认做法是决策参考。用户已明确的目标、项目当前有效约定及宿主指令和权限，需要在真实上下文中共同核对。本资料不扩大操作授权，不要求自动安装工具、创建 Agent、停服务、提交代码或发布。

## 证据与成熟度

规则区分以下来源，不能互相替代：

- **经验整理**：原材料记录过的实践，但本资料不证明它在新项目有效。
- **官方资料**：能核对的技术行为；版本敏感内容仍需对照项目锁定版本。
- **设计建议**：为提高可复用性新增或调整的方法，尚不能描述为已落地能力。
- **项目验证**：只有当前项目已有命令、交互、测量或恢复记录支持时，才标注对应范围通过。

## 维护规则

每条有价值的经验应说明：适用条件、怎么做、为什么、边界或例外、如何验证。条件明显且风险较低时，可以用短段落表达，不为每条强套模板。

当前默认值、路由、主题清单等随代码变化的事实，放在项目唯一事实源；这里记录判断方法，并引用相应位置。变更后修复引用，避免同时维护多份数值和清单。

生效入口保持现行口径。历史迁移、重要决策、事故原因和失效依据可以独立保留，并注明状态，不混作当前配置。新增经验先记录来源和验证状态；重复证明有价值后，再判断能否提升为通用方法。
