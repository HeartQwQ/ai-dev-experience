# 工程与协作经验

适用范围：代码定位、工具链锁定、实现协作、质量门禁、运行环境、数据保护与交付。本文为经验整理与设计修订；具体目录、命令、端口、进程、版本和发布制度以项目当前事实及用户要求为准。

## 一、仓库、子工程与工具链锁定

前后端或多语言子工程可以各自管理依赖和构建，也可以使用已有 workspace；选择依据是边界和协作需要，不为套 monorepo 模板搬目录或更换管理器。跨端契约（`packages/contracts/` 或绑定产物）和发布兼容仍需共同检查。

**多层可复现工具链与依赖锁定：**

- 跨语言运行时版本优先通过根 `mise.toml` 统一声明，Rust 工具链与 `rustfmt`/`clippy` 组件通过 `rust-toolchain.toml` 锁定，Node 包管理器通过根 `package.json` 的 `packageManager` 字段锁定。
- pnpm workspace 优先使用 `pnpm-workspace.yaml` 的 **`catalog:`** 集中声明跨子包共享依赖版本（如 `vite`、`svelte`、`tailwindcss`、`@biomejs/biome`、`vitest`），消除多子包版本分裂。
- Rust workspace 在根 `Cargo.toml` 集中定义 `[workspace.dependencies]` 与 `[workspace.lints]`，并通过 `deny.toml`（`cargo deny check`）守住许可证合规、RustSec 漏洞与注册表来源。

统一入口脚本适合固定工作目录、选择工具链与编排子工程命令，不复制业务实现。子工程自己的操作入口保持可用，失败能定位到具体步骤。脚本移动后重新核对根路径、输入、输出和调用方；索引、缓存、制品、依赖和运行数据的目录分开，排除规则按用途维护。

## 二、根据任务规模选择流程

先明确当前行为、预期行为、影响范围和可观察验收。目标清楚且局部可逆的小修复直接实现并验证，不强制需求文档、架构决策或逐步批准。

影响产品行为、公共接口、数据、部署或设计系统的变化，补充必要的需求、约束和取舍。只询问会改变重要决定的缺口，利用现有上下文作合理判断，同时推进独立工作；已有授权不因参考文档流程重复确认。

**规划和现状分开。** 需求说明预期，方案说明候选和计划，开发文档记录已落地机制。方案可以在实现前写，只要状态清楚；实现后核对差异，不能把计划写成能力已经提供。

需求变化时同步受影响的验收和实现，不要求一律从固定步骤重来。纯注释、内部整理和测试补充按影响决定是否更新文档，不为留痕制造产品变更记录。

## 三、代码定位、双图谱与系统级 Hook 门禁

先看相关规则、现有差异和必要元数据；查询项目业务代码前，依照[双图谱与 Hook 硬门禁](../graph-gate.md)建立并查询 `graphify` 与 `codegraph`，再以真实源码核实定义、引用和调用链。文本检索可补充图谱分析，不能替代门禁。任何摘要或索引只是线索，重要结论回到当前代码核实。

项目 `.agents/hooks.json`（调用 `tools/dev-spec/hook_gate.py`）在 `READY` 阶段自动对 `PreToolUse` 执行零信任拦截：若 `.dev-spec/local/graph-state.json` 或 `last-query.json` 缺失或与当前源码指纹不一致，系统将直接拒绝业务代码搜索与读取工具调用。

任一图谱工具或当前索引不可用时，暂停依赖代码分析的工作，先修复、重建并实际查询；不以纯检索替代。继续处理与代码分析无关的环境诊断和配置。用户明确变更此规则时按新要求执行。

按结构与行为查同类逻辑，避免只搜索旧名字漏掉改名或展开实现。查共享函数时核对外部契约与调用方，不能仅因重复就直接合并。

索引更新依工具机制和陈旧风险安排，不要求每次微小编辑全量重建。排除依赖、构建、数据与索引自身；变更排除范围后按工具要求同步。共享物理目录可能跨宿主可见，索引锁与并发重建需核对；只清理已确认陈旧的锁。

## 四、检查选择与证据边界

先遵守项目必需检查与 CI，再按本次风险选择补充。前端、后端和跨端变化检查各自受影响路径；认证、公共类型、共享 token、迁移等小文本差异也可能需要较广回归。

| 变化/风险 | 合适的现代工程检查 |
| --- | --- |
| 纯文档、链接或文案 | 文本差异、Markdown 内部链接校验、相关构建/实际呈现 |
| 前端静态、组件与交互 | Biome (`biome check`)、`svelte-check`、Vitest Browser Mode (Playwright Provider) |
| 函数、解析和数值规则 | `cargo nextest run` / Vitest 单测，必要时属性/差分与边界用例 |
| 跨端接口与存储 | `utoipa`/`tauri-specta` 契约同步检查、Testcontainers 真实测试库、Expand-Contract 迁移、权限与 RFC 9457 错误路径 |
| Rust 供应链与安全基线 | `cargo clippy --all-targets`、`cargo deny check`、Tauri v2 `capabilities/` 权限校验 |
| UI 行为/布局与无障碍 | 点击、输入、键盘、代表性视口、`@container` 响应及 Playwright + axe-core |
| 性能/资源 | 同条件前后对照，标注采样与样本限制 |
| 部署、迁移、备份恢复 | 配置预检、制品/实例标识、业务检查与恢复演练 |

检查受支持的目标和特性组合，不默认全目标全特性；互斥特性分别验证。需要明确目标三元组时沿项目配置传递，不给不接受该参数的格式化、审计命令硬加参数。

跨平台构建按所需链接器、库和 CI 确认能力；工具链缺失时可以使用已有 WSL、容器、远程构建或其他授权环境，不把 WSL 固定为唯一方案。离线模式只能用已有依赖，不表示在线审计已完成。

模拟界面、真实应用集成、受控外部环境和部署冒烟分别报告。mock 不能证明真实鉴权、联通、持久化或守护进程入口。

检查状态使用通过、失败、受阻、未执行、不适用。首次失败和复跑保留条件；局部复跑通过不改写为整套一次通过。环境限制只影响其对应结论，独立工作仍继续。

并行前核对账号/数据隔离、缓存、生成文件与制品目录。共享 Vite 依赖优化或构建产物可能互相干扰时复用合适服务或隔离缓存，不能以换端口冒充完全隔离；也不能把所有 E2E 都固定为单服务串行。

## 五、实例、双栈端口与运行版本

每个服务明确监听地址、端口配置、数据目录、启动入口、健康/就绪语义和实例所有者。配置可以有记录清楚的默认端口，也可以必须显式传入；不同入口保持有效配置和校验一致，不静默改变约定端口。

启动前在 IPv4 (`127.0.0.1`) 与 IPv6 (`::1`) 双栈核对当前实例和占用进程（`dev.py` 自动执行双栈预检）。需要复用、重启或另起实例由项目支持能力与用户任务决定；不得擅停其他程序，也不要悄悄换端口让浏览器继续连接旧实例。

**单实例约束作用于明确资源。** 独占数据目录或设备可要求单实例，多服务、只读副本和隔离测试实例可以并行。不能因“每个工作区一个进程”限制正常多服务开发，也不能复制生产数据绕过真实独占协议。

更新编译型服务时，确认新制品已构建并实际被目标进程加载。核对可执行路径、PID/启动时间、构建标识或哈希及实际行为；文件 mtime 只是辅助线索，不能证明运行版本。

健康成功只证明其声明的条件，不能代替 WebSocket、静态资源、身份和关键写入验收。开发服务器代理、跨域和环境注入代办的功能，在生产要明确由哪层提供。

## 六、热更新、进程清理与文件监视

按变更需要选择动作：前端 HMR、重新构建、进程重启或应用支持的配置热加载。嵌入制品的数据、迁移、工具链和脚本自身变化分别处理，不因任意文件变化重启全部服务。

监视器合并连续事件，构建进行时记录最新待办而非并发覆盖同一产物。构建失败时优先保留仍可用的实例；运行新版本前完成必要预检。

原生监听和轮询根据环境选择。跨挂载目录、文件替换或已证实事件丢失时可配置轮询；同时记录 CPU、延迟和排除目录，不一律要求轮询优先。

退出时管理自己创建的子进程树（Windows 64 位 Job Object / POSIX 进程组）和残留监视器；`Stop` Hook 会检查 `.dev-spec/local/dev-supervisor.pid` 是否残留。只按归属操作，不从端口号推断用户授权。验证 HMR 看实际消息与页面变化，验证重启看成功构建、进程/制品标识和业务结果，不只看文件时间。

临时探针结束后恢复本次改动，查看 diff 确认无残留，同时保留用户原有改动。测试失败构建时不要为了制造场景先停止可用服务，除非该测试确需且已获相应授权。

## 七、数据隔离、备份与恢复

生产、开发和自动化测试使用适合其用途的数据与权限边界。需要样本时优先脱敏或合成数据；复制真实数据取决于授权和隔离要求，不自动从生产灌入开发。测试结论说明使用的数据来源，不能拿开发快照推断当前生产状态。

先分类：唯一业务数据、配置/权限、审计历史、恢复日志、可重建缓存和可丢弃派生指标。不能因为目录叫 cache 就全部清理，也不能假设所有快照都可重建。清理规则显式排除不可丢内容。

**备份要求一致、完整、位于合适故障域并可恢复。** 可以采用数据库支持的在线备份（如 `pg_dump` / `pg_basebackup` 或 SQLite 在线备份 API）、可靠快照或停机复制；停机不是所有场景唯一方案。[SQLite 官方说明](https://www.sqlite.org/backup.html)。

数据库备份还需与相关外部文件、配置和事务记录保持应用级一致，不能用数据库快照证明所有文件都一致。活动库的单文件复制不能默认当作一致备份；停机复制也要确认所有写者结束，按存储机制处理必要日志和元数据。

备份位置、加密/访问控制、校验、保留、恢复点与恢复时间要求按数据价值确定。硬链接只是一种实现手段，指向活动可变文件的硬链接不能天然成为独立副本；不支持时选择已验证替代方案或明确失败，不能谎报成功。

恢复优先在隔离位置验证，核对记录、权限、外部路径引用和业务可用性。覆盖活动数据前确认实例停止和操作授权，保留故障现场。更换绝对路径需处理嵌入引用；代码版本恢复不等于数据恢复。

记录恢复演练，而不只确认压缩包存在。没有独立可用副本时不能承诺磁盘全损可还原；允许丢失范围与备份频率及一致性有关。

## 八、发布与回滚

发布按实际部署模型设计：单进程版本目录、容器、滚动或多服务都可能合理。先构建、检查配置和兼容，再进入切换窗口；预检失败保留当前服务，不把准备工作放在停机之后。数据库演进遵循 Expand-Contract 模式，保证滚动发布期间新旧版本实例可同时工作。

前后端需要耦合发布时成套切换；允许独立发布的系统则用契约兼容窗口。配置模板用于初始化或明确迁移，不在升级时覆盖现有用户设置。构建期变量变化需要重建相关产物，运行期变量由其读取机制决定。

同一部署资源的并发变更用适当锁或控制面协调。停止前核实进程归属，单实例切换等待旧实例完全退出；多实例滚动则按就绪与流量策略，不机械要求全停再启动。

新版本失败时按既定策略恢复可用版本并报告本次发布失败，恢复成功不吞掉故障。数据不兼容、外部副作用和不可逆迁移单独处理，不能声称切回二进制就恢复全部状态。

保留旧静态资源、版本或缓存兼容可以支持已打开页面，但范围、资源安全与保留预算按构建方式决定；不无条件从任意上一版本 fallback。清理前核对仍在使用的实例和资源。

发布、停止服务、数据恢复和外部写入需要符合本次授权和环境权限；已有授权时继续完成可行工作，缺必要授权时先准备可审核制品与方案，并说明具体需要的动作。

## 九、凭据、信任与诊断边界

认证材料可以由需要它的可信后端组件处理，不能笼统要求“不进入后端”；明确哪些组件验证、转交、保存或刷新，限制读取范围和生命周期。

凭据不能进入前端公开构建变量、制品说明、版本库、日志和错误报告。外部服务地址与秘密访问 URL 分开判断。用户主动提供的凭据也不意味着可以把它回显到诊断输出。

可信身份与对象授权的实现见[后端篇](01-后端-Rust-Axum-Tokio.md)，Web CSP/CORS 与 Tauri v2 Capabilities 最小权限见[前端篇](02-前端-Svelte-SvelteKit.md)。大小、类型、白名单、租约和限额需有理由地维护，变更时核对绕过路径和兼容性，不因测试方便放宽生产保护。

排查只读取必要资料，不默认新增监控、上传源码或发送外部消息。敏感真实环境操作依授权和工具权限执行，不能从文档示例获得操作许可。

## 十、文档与唯一事实源

项目规则放硬约束和入口，需求放用户预期，方案/决策放取舍，开发文档放已落地实现，部署文档放环境操作。相同清单和值只维护一个权威来源，必要类型或契约产物尽量由其自动生成/校验，引用不再抄总数。

当前配置入口删除或明确迁走失效内容，不能混放新旧默认值让读者猜。升级说明、弃用窗口、事故复盘和决策历史可以独立保存，并标明适用版本和状态，不要求抹除所有历史。

文档依据当前分支的真实接线核对；搜索到旧提交或其他分支只当线索。描述页面能力时看实际入口、权限与操作结果，函数或枚举存在不能证明界面已提供功能。

修改长文档可以精确替换或按明确范围重写，先确认完整输入，随后看差异和章节完整性，避免片段覆盖整文件。删改文件修复 Markdown 链接；待办保存当前事项，历史记录放合适位置。

经验条目标注原项目记录、官方核对、设计建议或当前验证，不把尚未采用的建议写成既有约束。新经验的收录可以早于落地，但成熟度清楚。

## 十一、版本与变更说明

沿项目既有发布制度，或在确需建立时选择有清楚含义的版本策略。语义化版本、日期或构建标识各有适用范围；合并/提交次数编码只能作为明确选择的项目制度，不是通用三段式含义。

### SemVer 与 0.x 迭代

- 采用 SemVer 时，先明确对外兼容范围，例如插件接口、配置格式、数据格式和命令行参数。稳定版本用 `MAJOR.MINOR.PATCH`，不兼容变更升主版本，兼容新增功能升次版本，兼容修复升修订号。主版本递增时将次版本和修订号归零，次版本递增时将修订号归零。[SemVer 2.0.0](https://semver.org/lang/zh-CN/)
- 每一段按整数独立比较。修订号满 9 继续加一，例如 `0.5.9 → 0.5.10 → 0.5.11`。版本比较应使用 SemVer 解析或逐段比较，避免用小数或字符串顺序比较。
- SemVer 将 `0.x` 留给初期开发，对外契约可能变化。对于采用快速迭代的内部插件，团队可约定小功能、界面调整和修复随每次实际交付增加修订号。功能阶段变化或契约变更可升次版本并将修订号归零，例如 `0.5.16 → 0.6.0`。对外契约稳定并准备承诺兼容时，再发布 `1.0.0`。
- 同一版本对应固定的已交付内容，后续修改用新版本。出包时核对版本清单、制品和变更说明一致，部署后另行验证实际加载的版本。

版本身份由清单、标签或发布系统等权威位置维护，其他展示由生成/检查保证一致，不规定全库只能写两处。开发分支推送不自动等于发布，也不要求每次推送改产品版本。

用户更新记录说明实际行为、影响和必要操作；开发者说明可包含接口、依赖、部署、破坏性变更和迁移要求。内部维护是否记录按受众决定，不能全删掉用户看不见但开发者必须知道的信息。

合并批次或自然发布时间组织均可，保持可追溯；纯文案修订是否发版依项目规则。事实描述简洁，避免“全面升级”等无证据套话，也不把计划能力写成已发布。

## 十二、Git 与协作

编辑前核对工作区差异，不覆盖或回退无关改动。拉取、切分支和合并前检查冲突风险；有未提交改动不意味着所有读取都禁止，但不能自动执行可能丢失或混入改动的更新。

提交、推送、创建 PR 或发布按用户已授权范围执行，不因文档习惯自行操作，也不对已授权动作重复确认。提交尽量聚焦逻辑变更，按项目语言/格式记录，避免将独立问题混在一起。

推送和发布前分别核对其所需文档与检查；是否更新版本和产品记录由发布制度决定。发布分支、主干或标签的关系以仓库实际流程为准，不声称所有项目只从主干发布。

回归可利用正常/异常版本与环境做差分或二分，保护起始状态。交付说明本次实际改动、结果和限制，用户原有差异不归功于本次任务。

## 十三、变更影响核对

删功能、改共享实现或默认配置时，沿入口、调用方、跨端契约、数据、权限、环境变量、构建/部署、文档和测试逐项查影响。字段迁移和历史保留按兼容需求（Expand-Contract）决定，不能机械删除所有数据库列或历史记录。

白名单、文件集合和扫描规则有多个消费者时，确认权威定义及派生关系，更新默认、部署示例和相关检查。产物路径变化核对构建、打包、托管和发布入口；先分清变量在构建期还是运行期生效。

共享实现改动核对字段缺失/空值、类型、排序、错误和权限语义，不把“收口”当作改变契约的许可。公共 token/组件变化核对代表性页面和交互态。

评审读取新增和删除内容，追踪实际调用路径和上一轮未关闭问题；只看到变更文件名不代表已经分析影响范围。

## 十四、排查与交付纪律

先记录错误与复现条件（利用 `dev.py` 自动输出的最后 30 行服务日志摘要），再通过双图谱查询定位并读取规则和真实源码，建立少量可证伪假设，以低成本观察区分。每轮形成观察、推论和下一步验证；多轮无新证据时扩大到配置、数据、网络、边界与时序，不反复重启或换端口碰运气。

断言需真实命中目标；空集合遍历、旧标题和 DOM 序号都可能制造假通过。验证脚本也要检查自己是否真的执行相关步骤，不能以退出码零替代覆盖确认。

强制终止信号不等于 OOM。核对内核/平台事件、PID、时间及有效控制组计数；日志不可读时说明无法确认，不能据此排除。应用预算拒绝与内核杀进程分别报告。

“页面能开但没数据”先查真实请求链路、接口错误和身份，再查数据；“改了不生效”先查实例、制品、HMR 和缓存。证据足以支持最小可逆修复时可以推进，验证不支持就调整，不要求等待不现实的百分之百证明。

交付按实际执行层级报告通过、失败和未验证项。静态、模拟、本地、真实外部与生产结果不合并；保留首次失败及重试事实。完成当前已授权任务后再交还，不以提出建议代替必要实现。
