# Rust / Axum / Tokio 后端开发经验

适用范围：使用 Rust 及相关运行时、HTTP 框架、PostgreSQL (`sqlx`)、SQLite 或文件持久化的后端任务。具体 API 以 Cargo 清单、锁文件、工具链和受支持的目标/特性组合为准。以下为经验整理与设计修订，不表示当前项目已验证。

## 一、工程分层与模块组织

**先沿现有边界组织职责。** 对没有独立部署、故障隔离或资源隔离需求的应用，模块化单体通常足够。应用装配、处理器、领域逻辑、存储、调度、配置和身份可以在进程内分层；已有多服务架构则先理解边界，不为遵循模板合并或拆分服务。

**路由和中间件的组装路径应可追踪。** 各领域可以暴露子路由构造函数，由装配层统一组合。核对中间件顺序、覆盖范围和 fallback，避免相同入口经过不同的身份或错误处理链。路由清单优先从实际装配或 OpenAPI 注册生成；文档描述契约，不另写易漂移的路由总数。

**启动前校验影响安全和服务可用性的必需配置。** 必填项和非法值尽早失败；明确允许缺失的可选能力可以关闭并报告状态。不要把“任意可选配置错误”都变成全服务不可用，也不要让必需配置缺失时悄悄降级。

只读配置与热更新配置分别建模。热更新可用不可变快照整体发布，加载失败保留有效旧值；是否需要撤销在线连接或重新排队，按权限生效和任务契约决定。读取配置的 I/O 放在适当的后台或异步边界，避免阻塞请求执行器。

运行期数据、配置和日志路径由配置层解析，避免与构建目录耦合。制品是否内嵌静态资源按部署选择；制品不应覆盖用户现有配置和业务数据。相同语义的常量与集合维持唯一事实源。

## 二、路由、处理器与授权

稳定接口优先使用明确的请求/响应结构和枚举，便于校验、重构和契约检查。动态 JSON 适合形状确实动态的边界，不因它灵活而跳过验证，也不把它一概禁止。

**不要让可预期的输入错误依赖 panic。** 用可恢复错误表达缺字段、越界、找不到对象和状态冲突。`unwrap`/`expect` 是否可接受取决于前提能否证明；请求可达路径需要特别审查。panic 的影响取决于构建策略、任务边界和运行时，不能直接等同为进程终止。

**认证、对象授权和审计身份分别核对。** 身份可以由统一中间件验证并注入，但“已登录”不代表有权访问任意对象。具体资源与动作的授权放在能取得必要上下文的位置，可以是中间件、处理器调用的授权服务或领域边界，保持一致且便于测试。

若依赖网关注入身份头，需要确认客户端无法绕过网关或伪造可信头。请求体里的“操作人”不能作为可信审计主体；确有代操作需求时，发起人和被代理人分别建模并授权。身份规范化按提供方契约执行，不随意把区分大小写的标识转小写。

入口校验语法、必填、范围和大小；领域层维护业务不变量，存储层用必要约束守住并发。健康检查、指标和静态资源是否公开、是否限流，按暴露范围与部署要求决定；fallback 不得吞掉 API 的权限错误或不存在响应。

## 三、状态、连接池与后台任务

共享依赖通过框架状态类型或显式参数提供，避免不可替换的隐式全局单例。状态应便宜克隆，昂贵内容按所有权和生命周期共享，不能为绕过借用检查复制大 buffer。

连接池容量结合并发、事务耗时、数据库锁竞争和测量选择。区分连接级设置与数据库级设置：PostgreSQL 连接池显式设置 `max_connections`、`acquire_timeout`、`idle_timeout` 与会话级 `statement_timeout`；SQLite 外键、`busy_timeout` 等按连接核对，WAL 是否启用按实际存储环境与数据库配置决定，不在每次借连接时盲目重设。不要把“小池足够”当作容量结论。

热配置的读取与发布保证一致视图。不可变快照、短锁或其他机制按实际读写频率选择，不为所有共享状态强制异步读写锁。

每个后台任务明确创建者、拥有者、取消/关闭信号和等待策略。退出时决定排空、超时、持久化后恢复或中止；有副作用的任务不能只因句柄被丢弃就视为完成。

## 四、PostgreSQL (`sqlx`)、SQLite 与零停机迁移

**通过版本化迁移管理 schema，生产演进遵循 Expand-and-Contract（扩展-收缩）模式。** 沿用现有迁移工具（如 `sqlx migrate`）；小型单机项目可以用 `PRAGMA user_version` 等机制，但不强制替换成熟方案。已发布迁移保留语义，新增迁移考虑空库、旧库数据、支持版本和失败恢复；高于程序支持范围的库按兼容策略拒绝写入或拒绝启动。

**PostgreSQL 生产级规范：**

- **编译期 SQL 校验**：优先使用 `sqlx::query!` / `sqlx::query_as!` 并在无数据库的 CI 环境中维护 `.sqlx/` 离线元数据（`cargo sqlx prepare --workspace --check`），在编译期拦截表名、列名与可空性漂移。
- **在线无锁变更**：大表新增索引使用 `CREATE INDEX CONCURRENTLY`（注意该语句不能运行在显式事务块内）；新增带非空约束的列分两步（先加可空列或利用 PG 原生常量默认值元数据特性，再使用 `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` 避免长表级排他锁）。
- **零停机两阶段迁移（Expand-Contract）**：禁止在单次滚动发布中直接删除、重命名或修改旧版运行实例仍在读写的列；先在阶段一扩展兼容列并双写/回填（Expand），待旧实例全部下线后再于后续版本清理旧列（Contract）。

**事务与 SQLite 专项：**

同一原子单位的批量写优先在一个短事务内完成，复用 prepare 或使用批量 `UNNEST` 绑定，减少重复提交开销。大批量若需分块，应先明确部分成功、断点与重试语义，不能以性能为由打破原子承诺。提交是否触发磁盘同步取决于 `synchronous_commit` 或 SQLite `journal`/`synchronous` 等配置，不把每条语句简单等同为一次 fsync。

SQLite 读后写事务可评估 `Immediate` 以更早发现写锁竞争，同时核对 busy 处理和锁持有时间。网络、长计算和用户审阅不放进数据库事务；准备好数据后再进入短写入边界。

查询优先显式列名和参数绑定。识别 N+1 时核对调用次数、批量查询规模和查询计划，不能为避免循环而产生超大无界查询。复合索引通常受前缀约束影响，但缺少最左列并不必然不能利用索引；SQLite 存在 skip-scan 等策略，依据实际版本、统计信息与 `EXPLAIN QUERY PLAN` / `EXPLAIN (ANALYZE, BUFFERS)` 判断。[SQLite 官方说明](https://sqlite.org/optoverview.html#the_skip_scan_optimization)。

同步驱动的数据库等待与操作按耗时放到适当执行边界，不长占异步线程。事务失败保留原错误，附加恢复/清理失败信息，不用清理报错覆盖根因。

## 五、异步、阻塞与取消

阻塞 I/O 和长 CPU 计算不能长期占用异步执行器。根据操作能力选择异步 I/O、`spawn_blocking`、专用线程或受限 CPU 池；不把所有很短的内存操作都迁移到阻塞池。

CPU 密集工作需要独立并发预算。阻塞池允许的线程数量不等于业务能承受的并行量；还需控制排队对象数量和输入大小，避免只限制“运行中”却堆积无界队列。

**停止等待、取消任务和撤回副作用是不同动作。** 已经开始的 `spawn_blocking` 不能用 `abort` 强制停止；超时只结束等待也不会释放其真实工作。资源许可与文件锁由执行该工作的所有者持有，直到实际结束或安全回滚完成。[Tokio 官方说明](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。

纯计算或分块工作可在安全检查点协作取消；写到一半不能安全退出的阶段，采用明确收尾、补偿或恢复机制。对这些关键边界说明取消语义，不要求每个普通 async 函数重复标注。

全局、资源、账号或执行端的限额按瓶颈和正确性需要选择；租约适合任务可能失联的分布式或代执行流程，不是所有函数的必备参数。退避、抖动、截止时间和重试预算按可重试错误设计；更换执行端前确认不会重复执行未知结果的副作用。

## 六、错误处理（RFC 9457）、解析与幂等

错误形状和稳定错误码沿用现有契约；**新项目或新 HTTP API 优先采用 [RFC 9457 Problem Details (`application/problem+json`)](https://www.rfc-editor.org/rfc/rfc9457.html) 标准结构**（包含 `type`、`title`、`status`、`detail`、`instance` 及机器可读扩展字段如 `code`、`trace_id`、`errors`），不为统一外观破坏旧调用方。HTTP 状态反映请求语义和认证/授权/冲突等实际原因，不能把所有可重试错误统一视为 503。

内部保留错误链（`source` / `anyhow` / `thiserror`）和必要上下文，对外返回受控摘要。凭据、原始敏感输入和不受控上游错误体不能直接进入响应或日志。可重试错误说明条件与方式；校验失败、权限不足或需要重新审阅的冲突不能盲目重试。

解析策略取决于输入契约。处理安全敏感配置或受支持语法子集时，未知语义、超深结构或不支持表达式应明确拒绝，避免静默改变含义；兼容读取可以按明确规则保留未知字段或返回部分结果，但必须让完整性可辨认。

幂等用于同一意图的重试不重复产生副作用。若使用幂等键，要明确键作用域、有效期与参数比对；同一键携带不一致意图可以拒绝。普通更新把旧值改为新值是合法操作，其并发冲突由修订号、条件写或事务处理，不能用“相同位置不得改不同值”代替。

## 七、日志、Tracing 与 OpenTelemetry 可观测性

日志与追踪输出适配部署环境。容器可由 stdout/stderr 采集 JSON 结构化日志或通过 OTLP 导出遥测数据，本地独立服务可以写文件；只有确有需求才双写，并核对重复采集、磁盘预算和故障策略。

**统一使用 `tracing` 生态建立结构化 Span 与事件。** 关键入口与跨边界调用使用 `#[tracing::instrument(skip_all, fields(req_id = %..., user_id = %...))]`，显式 `skip_all` 防止将包含密码、令牌或大体积字节流的请求体自动序列化进日志。HTTP 服务通过 `tower-http::trace::TraceLayer` 与 W3C `traceparent` 头打通前后端 Trace ID，使错误响应中的 `trace_id` 可直接关联后端链路。

凭据、完整认证头、会话和可直接使用的秘密地址不落日志。对象标识与输入片段也需按敏感性最小化；保留原始信息应有明确诊断必要性、脱敏和访问控制。

文件日志才需要配置轮转、保留天数、容量上限和权限。Unix 权限与 Windows ACL 按平台处理，不把 0600 当作所有系统通用 API。清理只处理本组件拥有且允许删除的文件，不跟随不明链接、不删除业务数据。日志写失败是否阻断服务取决于审计要求；可选统计失败可降级，但不可伪造成功。

性能采样记录口径、间隔和限制；采样不可用不是零值，采样 RSS 不是精确峰值。监控和外部上报沿现有授权与部署能力，不作为普通修复默认新增项。

## 八、契约驱动开发（Contract-First）、批量与并发更新

**跨端接口以单一代码契约为唯一事实源（Single Source of Truth）：**

- **HTTP 服务**：优先在 Axum 处理器与请求/响应结构上派生 `utoipa::ToSchema` 与 `#[utoipa::path]`，导出标准 OpenAPI 3.1 文档至 `packages/contracts/`，再通过 `openapi-typescript` 或 `orval` 生成前端严格类型客户端。
- **Tauri v2 桌面命令**：优先在 `#[tauri::command]` 上配合 `specta::Type` 与 `tauri-specta` v2 自动生成前端 TypeScript 绑定文件，禁止前后端各自手写一套 DTO 造成字段名、枚举变体或 `Option<T>` 语义失配。

契约变化同时核对生产者、消费者、缓存和兼容窗口。缓存结构版本、数据库迁移版本与公开 API 版本各有职责，按实际不兼容变化演进；新增兼容字段不机械升级所有版本。

异步结果按当前操作与资源标识匹配，不能用全局“最近成功”替代本次结果。审计记录保存事件发生时可信身份、目标与来源；缺失历史元信息明确记未记录，不借当前状态补造过去。

预览接口是否允许创建临时任务、保留草稿或提供撤销，需在契约中明示；“预览”不能偷偷执行最终业务写入。限流键考虑可信身份、来源、租户和资源，控制维度应与共享额度及滥用风险一致。

批量 API 可减少往返，但先定义原子单位：全批事务、分块、逐项结果或工作流。明确大小上限、部分结果、幂等、失败后恢复和客户端清理方式；不能从“一次 HTTP 请求”推导“天然全成全败”。

字段级 patch 有助于减少覆盖范围，但仍需修订/条件检查；整文档替换也可以在具备可靠条件写时使用。删除与重新创建可能引入版本复用问题，按真实模型选择墓碑、不可复用标识或版本生成方式。

## 九、文件持久化与跨系统写入

**先声明保证，再选择协议。** 区分读者看不到半文件、进程崩溃可恢复、掉电持久化、多文件一致及远端原子条件写。这些不是同一个保证。

同类单文件提交集中维护经过验证的实现。临时文件通常放在同一文件系统，避免意外覆盖，正确处理刷盘、替换、权限、目录与失败清理；具体保证依赖操作系统、文件系统和 API，不能把一套 rename/fsync 顺序视为跨平台充分证明。

多文件联合更新可以选择数据库事务、日志恢复协议或版本目录/指针切换。若依赖日志恢复，需在破坏性副作用前持久化足够的目标身份、基线、意图或恢复内容；定义提交点、完整性校验和重放幂等，保留未完成事务依据。对每个阶段的崩溃和清理失败做故障注入，不能只验证正常路径。

跨系统操作明确未发送、发送中、结果未知、确认失败、确认成功及本地记账状态。关键收尾可以脱离 HTTP 等待生命周期，但必须有受管理的拥有者、恢复记录和可查询结果，不能只派生一个无人管理的任务。

### 可选案例：缺少条件写能力的远端文件提交

适用：确实需要浏览器/执行端代写远端文件，且已经确认远端 API 能力。该案例是设计参考，原材料中的实现细节未在本轮运行验证。

- 准备固定候选内容、基线指纹和操作 ID；发送前复核基线，可以发现已发生的冲突。
- 本地 claim/租约与每资源锁只协调遵守该协议的参与者，不能防止外部系统在复核后写入。租约失效还需处理旧执行者迟到，不能当作远端条件写。
- 若需求要求绝不覆盖外部写者，需要远端原子版本检查、可信全局协调或改变操作流程；缺失这些能力时明确剩余竞态窗口，不给出绝对保证。
- 内容相同只证明某时刻结果一致，不能单独证明是本次操作造成。审计归因应有操作结果或协议证据；确认与记账按操作 ID 去重，不能覆盖后续更新。
- 取消仅处理尚未发送或可安全撤回阶段；结果未知先查询/协调，不直接重发。失败保留恢复依据，支持在线恢复；不强行回滚已经确认的外部新状态。

上传、接收与解压设置实际读取的压缩体/展开体上限、并发和队列预算；客户端声明长度只作辅助信息，不替代实际字节校验。

## 十、并发与锁

按临界区耗时、是否跨 await、等待方式和公平需求选同步原语。短且不跨挂起点的临界区可用同步锁（如 `std::sync::Mutex` 或 `parking_lot`）；长等待优先缩小锁范围或改为适合异步等待的设计。避免持阻塞锁跨挂起点（启用 `clippy::await_holding_lock` 检查），涉及多锁时记录并维持一致顺序。

清理大集合的全量遍历会拉长持锁时间，可分批、分片或采用有界过期机制；集合很小且有硬上限时不必为此引入复杂结构。锁内 I/O 只在协议确需串行且影响可接受时采用，并核对取消与恢复。

同一资源重复重建可以合并为一个运行任务和最新待办，排队只存标识，避免提前加载大对象。取锁后重新校验版本，完成、失败和取消都清除登记；源版本变化时不要激活陈旧结果。

读快照、写构建与发布边界分开。相同只读内容可以按版本共享；用户权限和可编辑派生状态不能因共享缓存而串用。

## 十一、缓存与失效

缓存键包含真正影响结果的输入、身份/租户、算法与结构版本；内容指纹适合内容驱动派生，但并非所有缓存都需重新读取全量内容求哈希。修改时间可以是辅助信号，不能作为对内容一致性要求很高场景的唯一依据。

大内容指纹流式计算；只物化查询需要的字段，避免为了展示名称重新解析完整输入。投影仍需满足约定的语法验证与数据完整性要求。临时对象用完及时释放，是否常驻完整结构以复用收益和预算决定。

损坏/不兼容缓存不能返回成有效结果。可重建时按未命中处理并受预算约束地重建，同时记录必要诊断；唯一业务数据损坏不能冒充普通缓存清理。文件缓存的原子发布复用第九节约定。

命中与未命中的公开响应契约保持一致；降级或部分结果显式表达。派生指标若要跨重启累计，应保存必要样本权重和时间范围，不仅累加日均值；它是否可丢弃由产品要求决定。

## 十二、性能与内存管理

先确定用户路径、数据规模、耗时和内存口径，再做同条件前后对照。行为等价按接口语义比较；只有字节本身属于契约时才要求逐字节一致。不要用单次采样或代码行数推断收益。

大分配之前评估预算，考虑实际容器/控制组及有效祖先限制、进程其他负载与安全预留。准入降低资源风险，不能保证绝无 OOM；估算系数需要真实受限环境校准，不能用解析结束后的 RSS 自动调低。

优先检查同时驻留的原文、token、AST、中间结果和索引。可行时流式消费、少量前瞻、字段投影并及时释放；解析、遍历、格式化和析构都考虑异常深度。不要把所有解析器强改为流式，先验证语义与复杂度。

只有明确分配器、平台和性能代价且测量支持时，才评估主动归还堆页；这不能替代减少重复表示。阶段计时区分排队、解析、组装、持久化及查询。

### 历史观察的使用边界

原材料记录过“约 30MB 输入对应约 800MB 新增占用”的现象，但未提供可复核的版本、输入、分配器、限制与采样记录。本条仅提醒检查多份表示同时存活，不能用来推算新项目放大倍数、容量或限额。

复现记录应附输入特征、工具链/依赖、构建模式、分配器、CPU/内存限制、并发、冷/热状态、各阶段存活对象和采样方式。测不到精确峰值时如实称采样值。

## 十三、测试与验收

新增接口/任务关注输入、对象授权、RFC 9457 错误与契约导出、幂等与重试、错误传播、审计和恢复。具体用例由变化风险决定，测试层级与结果记录统一见[工程与协作](04-工程与协作.md)。

优先使用 `cargo nextest run` 执行进程级隔离单测与集成测试，使用 `cargo deny check` 校验依赖许可证与安全漏洞。单元验证解析和计算，Tower `ServiceExt::oneshot` 与 Testcontainers 验证接口与真实数据库迁移，关键任务验证真实用户路径；mock 的证明范围单独报告。涉及并发/恢复时覆盖旧修订、重复意图、结果未知、迟到任务和故障边界；性能工具与服务运行逻辑分开。

遵守项目必需 CI，并选择受支持的目标/特性矩阵。共享层或契约变化要重新生成前端绑定并扩大到受影响调用方；纯文档/文案检查选择链接、构建或渲染等适合内容的方式，不机械要求只做类型检查。
