# UI 设计经验与可选风格预设

适用范围：页面、组件、表单、表格、导航、主题和公共视觉系统。本文为经验整理与设计修订，覆盖多种产品；原材料中的桌面密集工具风格集中放在第十五节，未选用时不作为项目默认。

异步与提交状态转换见[前端篇](02-前端-Svelte-SvelteKit.md)，任务规模、检查与交付见[工程篇](04-工程与协作.md)。本篇维护用户任务、OKLCH 视觉表达、`@container` 容器响应式、布局与 WCAG 2.2 可访问性方法，不复制框架 API 规则。

## 一、先明确任务与设计基线

先识别用户、主要任务、使用频率、内容密度、设备和输入方式。阅读、移动表单、数据工作台与营销页面需要不同的信息节奏，不能直接复用同一个后台骨架。

已有设计系统时优先继承有效的组件、状态和 token；新项目先做代表性任务页与关键状态，再确定可复用体系。现有组件不足或用户要求改变产品语言时可以调整公共层，不把组件库初始外观当作永久约束。

优先解决信息结构、对齐、密度、排版和操作反馈，再选择颜色与装饰。渐变、模糊、半透明和阴影按意图、可读性、性能、主题和支持范围使用，不能靠增加效果弥补任务不清。

## 二、页面结构与信息层级

从主要任务确定导航、当前作用域、任务分区、字段和辅助信息。高风险或待处理信息需要适度强调，但不把所有“有变化”都用危险色。

App Shell 适合持续切换模块的工作台；阅读页和轻量表单可以使用更简单结构。顶栏、侧栏与内容基线保持有意图的对齐，窄屏允许重排和自然增高，不用固定高度遮住换行内容。

卡片、分隔、留白、区域底色都可以表达分组。避免无意义的嵌套容器；同样不因为“不套卡片”而禁止确有独立任务的卡片集合。区块标题、描述和工具栏只保留理解与操作需要的部分。

重要任务先设计初始、加载、空数据、错误、无权限、编辑、冲突和结果未知，再补视觉细节；具体需要哪些状态取决于任务。

## 三、排版与内容密度

字体选择结合受众、平台、品牌、字符覆盖和加载预算，中文工具界面可优先系统中文 UI 字体；需要专门字体时验证回退、混排和性能。

代码、哈希、路径可使用等宽字体，数值列使用 `font-variant-numeric: tabular-nums`（Tailwind `tabular-nums`）保证等宽数字纵向对齐以便比较；时间戳是否等宽根据任务选择，不是所有内容都套一种文本样式。

字号、行高、字重和间距按可读性与密度设定，不把 12px 正文或 18–20px 标题当作通用门槛。支持缩放、长中文、数字和混合字符，关键操作不能因缩小字号勉强塞进界面。

截断要有合理获取全文的方式，换行不得压住邻近操作。表格的强调层级与阅读页不同；标题是否大字根据产品语言，不统一禁止营销型标题。

## 四、颜色与语义 token（Tailwind v4 `@theme` + OKLCH）

复用的颜色语义集中维护，如基础背景/前景（`background`/`foreground`）、容器（`card`/`popover`）、主操作（`primary`）、次级（`secondary`/`muted`）、边框（`border`/`ring`）、警告（`warning`）、成功（`success`）和危险（`destructive`）。品牌原始色、语义用途和组件映射分层定义；单次装饰资产的颜色也要与体系协调，不把所有位图像素当作业务 token。

**新项目优先使用 Tailwind CSS v4 的 CSS-first `@theme` 指令与 OKLCH 感知均匀色彩空间（`oklch(L C H)`）定义语义变量**，利用一致的感知明度（`L`）与色度（`C`）阶梯管理浅色/深色主题与交互态，同时核对实际 sRGB/P3 显示器上的对比度和回退结果。

颜色不要作为状态唯一信号，配合文本、图标、结构或原生语义。危险、警告与普通变更区分；分类可以用可辨认且非唯一载体的配色，不为“丰富”随意分配大量高饱和背景。

悬停、选中、按下和焦点应可辨认，但不强制每种都用不同底色或按明度单向排序。主操作可实底、描边或其他体系允许形态，只要优先级清楚且可操作。

## 五、形状、边界与组件变体

圆角使用项目语义尺度，可为单一值或多级值；默认大小由产品决定。胶囊、圆形、直角拼接和继承关系按结构使用，不把所有 token 强制指向 8px。

边界可通过留白、底色、描边和阴影表达。按钮可以是平面或抬升，输入框可以有边框、底线或其他明确形式；不要求全部有高光、近影或内阴影。

同类组件优先共享尺寸和变体，业务调用不要无理由逐处覆盖。但公共体系可以扩展新变体，必要的局部例外记录原因并限制范围，不为追求“一套外观”妨碍真实任务。

## 六、区域面与层级

区域层级随信息架构建立，可以区分外框、导航、内容和浮层，也可以保持同一平面。相邻区域同色并不自动是缺陷，可用分组、间距、排版和边界建立关系。

同一主题可以使用不同色相来表达品牌、语义或内容分区，重点是意图清楚、不过度竞争和对比合适。纯白、纯黑及低彩度面都不是全局禁项，是否使用由实际视觉与可读性决定。

原材料中的“明度差 0.04/0.02”没有完整色彩空间和实验条件，只能作为历史调色案例，不能视为人眼阈值或无障碍标准。色彩空间中的 L 差、相对亮度与文字对比是不同量，不能用区域面差值证明文字可读。

层级修改在公共 token 或组件层集中维护，并检查所有主题及前景关系。深色主题不必机械反转浅色配色，也不必须靠发光表达层次。

## 七、材质、动效与系统偏好降级

材质可以完全平面，也可以采用柔和阴影、边缘高光、渐变或轻微透光。选择后统一复用可维护的 token 与组件，不把特定三层阴影称为所有浮层的必要条件。

半透明与模糊（`backdrop-filter`）需要在不同底层内容、主题和低性能设备上验证；不支持或开启高对比度模式（`@media (prefers-contrast: more)`）时回退高可读实色与清晰实线边框。不要重复叠加多个组件自带效果，修复时先确认公共和局部层的职责。

光源方向、阴影与高光在选用具象材质时保持协调；焦点可见性不能只靠模糊辉光。动效服务于定位和状态理解，允许取消并**强制遵守 `@media (prefers-reduced-motion: reduce)` 系统偏好**（将位移/缩放过渡降级为瞬时或柔和透明度变化，停止非必要循环动画）；长流程不能靠不可中断的演示推进。

## 八、主题与明暗模式

主题可以是单维互斥选项，也可以是品牌主题与明暗模式的组合，取决于产品要求和维护成本。先确定模型，再实现状态、持久化和第三方组件联动，不硬编码成某一种维度。

主题清单与语义定义有唯一事实源；运行状态和可用选项尽量生成或校验，避免两份清单手动漂移。类名、`data-theme` 属性或 `@custom-variant dark` 选择器均可，只要优先级、作用域和叠加逻辑清楚，并同步设置 `color-scheme: light dark` 以让原生滚动条与表单控件匹配主题。

首帧恢复和系统偏好按渲染模式及项目 CSP 等约束处理，避免闪烁（FOUC）与水合不一致。检查菜单、弹层、提示、表单和图表是否跟随语义，不只检查页面背景。

新增主题不必复制全部字面色值，但所有相关语义都应有完整有效的最终取值。主题专属效果限制作用域，不改变其他主题的状态和对比。

## 九、状态语义与反馈

同类状态在项目中保持一致含义，但允许不同组件用适合其结构的表达，不把所有选中都做成同一种品牌底。

| 状态 | 应保持的语义与行为 |
| --- | --- |
| 悬停/按下 | 让指针操作反馈可感知，不能替代键盘焦点 |
| 选中/当前项 | 清楚标记对象与范围，使用适当 `aria-selected` / `aria-current` 等语义 |
| 焦点 | 用户能看出当前键盘位置（符合 WCAG 2.2 焦点外观对比与面积要求），且不被浮层或裁剪遮住 |
| 不可用 | 真实不能操作，保留可识别轮廓与必要原因，不与当前项混用 |
| 待提交/有修改 | 反映当前草稿或任务，不等同错误和危险 |
| 加载/刷新 | 与已有内容、阻塞范围相匹配，避免全页无理由禁用 |
| 错误/冲突/结果未知 | 原因与可采取动作清楚，未知结果不冒充失败 |

禁用可采用降透明度或中性色等方式，选择后核对可读性和识别，不同时维护互相冲突的通用规则。`aria-disabled` 不会自行阻止事件，真实行为必须对应。

按钮不必全部从表面“浮起”，ghost/链接类仍可成立；可点击性靠整体结构、状态、标签和必要边界表达。输入框聚焦不强制从凹陷变浮起，关键是可编辑性、错误与焦点一致可辨。

## 十、列表、详情与表格

### 列表与详情

列表行层级服务于扫描、选择和操作。辅助信息可用文本、徽标或图标，保持对齐与可读；名称和计数不因装饰争抢注意。

同一任务跨分栏时对齐必要基线，不用独立内容高度导致关键信息跳动。详情分组依据任务关系，不一律禁卡片，也不把每个只读字段都包装成独立展示卡。

编辑入口显式可发现；保存、重置和批量操作按真实作用域布置。页面、分区、逐行或自动保存均可，但反馈与提交单位必须一致，具体状态机见前端篇。

### 表格

保留表头、列关联和必要说明，根据内容设列宽。宽表可使用局部横向滚动或其他符合任务的适配，不为“响应式”强行破坏行列比较，也不以表格为由让页面其他内容不可重排。

表头吸顶、行分隔、纵线和交替底色按密度、扫描、编辑与可访问性选择，均不是通用禁项。吸顶需核对滚动容器、遮挡、键盘焦点和窄屏占用。

同类表格共享可复用原语和样式；不同业务功能不强求同一巨型表格组件。删除标题/工具栏后检查空白和焦点入口，长内容与首尾列都需可达。

### 滚动条

默认保留平台习惯与滚动可发现性。滚动条可以随系统自动显示；不能因视觉整洁统一隐藏所有页面的滚动提示。确有沉浸式局部需求时，先验证替代提示、键盘、触摸、缩放和目标用户条件，不应用到整个站点。

## 十一、布局骨架、容器查询（`@container`）与滚动容器

阅读页通常适合自然纵向滚动；编辑工作台可使用固定外框与内部滚动；移动表单需考虑软键盘和动态视口（优先使用 `dvh` / `svh` 而非易被移动浏览器地址栏遮挡的 `100vh`）。先选模型再设高度，不把禁止整页滚动当作通用原则。

**可复用业务区块与卡片优先使用 CSS Container Queries（`@container` / Tailwind `@md:...`）根据父容器实际可用宽度响应布局**，避免仅依赖全局视口媒体查询（`@media`）导致侧栏展开/收起或分屏面板中组件挤压错位。

需要内部滚动的 flex/grid 布局，检查中间容器的最小尺寸和可收缩能力，必要时设置 `min-height: 0` / `min-width: 0`。加载、错误和内容状态不应因高度约束缺失产生跳动或遮挡。

减少无收益的嵌套纵向滚动；独立长列表、固定大表或并列面板确需内部滚动时可以使用，检查滚动接力和键盘到达。横向和纵向由哪个容器负责要明确，不能用外层裁剪消灭溢出内容。

二维滚动的例外应限定在需要二维布局的表格等区域，其他内容仍需适应缩放和窄视口，不能把例外扩大为整个页面。[W3C Reflow 说明](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)。

## 十二、可访问性（WCAG 2.2）与真实操作

优先原生按钮、链接、输入和表格语义。控件有可访问名称和适当标签；错误与输入通过 `aria-describedby` / `aria-invalid` 关联，反馈播报根据紧急程度选择，不把所有动态文本设成高优先级 `alert`。

**遵守 WCAG 2.2 核心交互硬指标：**

- **目标尺寸下限（WCAG 2.5.8 Target Size Minimum）**：所有独立指针可点击/可触控控件的交互热区或含等效安全间距尺寸不小于 **24×24 CSS 像素**（移动端及高频操作推荐 ≥ 44×44 CSS 像素），禁止因紧凑排版制造极窄的裸图标点击区。
- **焦点可见与不遮挡（WCAG 2.4.11 / 2.4.13 Focus Not Obscured & Appearance）**：键盘焦点使用清晰的 `focus-visible` 轮廓（推荐 2px 实线环及适当 offset，对比度 ≥ 3:1），且聚焦元素不能被吸顶表头、底部浮动工具栏或非模态浮层完全遮挡（配合 `scroll-margin-top`/`scroll-padding`）。

弹窗检查打开、关闭、Tab、Esc、焦点圈定（Focus Trap）与焦点归还；组件库提供能力仍要验证当前组合没有破坏它。颜色、动画、悬停和纯图标不能成为唯一线索。自定义复杂控件按其真实语义和键盘模式实现，不为每个数字文本强加 `spinbutton`；原生属性与 ARIA 保持一致。

检查缩放、长文本、窄屏、触控和键盘。临时视觉副本不接收交互、焦点并对读屏隐藏（`aria-hidden="true"` + `inert`），真正内容仍可操作。自动扫描不能代替实际任务；没有浏览器或真实页面时，报告静态发现及未验证范围。

## 十三、修改公共层

改 token、基础组件、通用布局和状态表达前，查代表性依赖与既有局部覆盖。确认问题属于公共语义还是单一业务，避免局部故障导致全局过度调整。

相关前景、背景、边框和交互态成组检查；跨主题验证，不只看当前页面的一张截图。新增状态或变体在唯一事实源维护，通过实际用法和检查防止漂移。

第三方包源码不因告警盲改；项目拥有的生成/拷贝组件可按维护策略修复，记录与上游更新的关系。视觉变更保持任务范围，不顺手重建全部组件体系。

## 十四、设计与验收闭环

设计前明确任务与状态；实现时复用有效组件并处理真实数据形态；验收先看结构和操作，再看字体、颜色与装饰。相同视口对照参考图，但不从图片推断未展示的业务行为。

桌面、分屏、窄屏、长内容、错误和键盘按受影响路径覆盖。实际点击输入并到达首尾内容，保存截图与必要操作结果；DOM 中存在元素不是用户可达证明。

记录发现、条件、影响与验证状态。纯静态检查不称为渲染验收，局部扫描不称全站无障碍通过。改动无实测收益或破坏既有任务时调整方案，不用“统一风格”解释可用性退化。

## 十五、可选预设：桌面密集工具

这是原项目经验的风格化整理，**默认不启用**。适用于键鼠操作频繁、数据密集且产品明确选择此风格的工作台；不自动用于阅读、营销、移动表单或其他品牌体系。以下是可选参数，采用后仍需满足前述可用性与 WCAG 2.2 可访问性（含 ≥ 24×24px 点击目标）。

| 选择项 | 可选做法 | 使用前核对 |
| --- | --- | --- |
| 密度 | 紧凑排版，`tabular-nums` 数字对齐，少层嵌套 | 缩放、长名称、≥24×24px 点击目标与触控需求 |
| 圆角 | 常规组件以 8px 为起点，特殊形状单独定义 | 品牌与已有组件尺度，不作为通用默认 |
| 区域面 | 外框/导航/内容/浮层采用 OKLCH 协调低彩度层级 | 同色面也可成立；没有固定明度差保证 |
| 材质 | 可选近/远影、边缘高光或统一光源渐变 | 性能、各主题阅读，不要求三层阴影 |
| 列表 | 品牌淡染和结构标记表达选中 | 不能只靠色差，不与禁用混用 |
| 编辑区 | 结构化分组或就地编辑 | 提交单位、错误反馈与键盘操作 |
| 表格 | 简化网格、按需关闭斑马纹/吸顶 | 长表扫描、定位和操作不能退化 |
| 外框 | 明确需要时采用内部滚动与完整高度链 | 所有状态、窄屏与软键盘下仍可达 |
| 主题 | 可以选择单维互斥主题以减少组合 | 用户是否需要独立明暗/系统偏好 |

滚动条统一隐藏、表头禁止吸顶、内容禁止纯白和固定明度阈值不作为本预设默认。确需局部特例时记录意图与验证，不借“沿用风格”绕过任务检查。
